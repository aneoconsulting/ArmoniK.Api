#   guard:          on
#   counting build: YES -- section 4's timings are NOT usable
#   rounds: 15, interleaved; per-round target 25 ms

#   arms
#     prost                today's floor, the baseline every ratio is against
#     core-native          the same traversal with no boundary (R3's control)
#     core-ffi-push        ak_decode_*: the codec calls the host per field group
#     core-ffi-pull        ak_parse_* + ak_bdr_drain into host memory + replay
#     core-ffi-pull-walk   ak_parse_* + ak_bdr_ptr + replay in place, no copy
#     core-ffi-pull-opaque the same walk with the replay's calls made OPAQUE, so
#                          rustc can neither inline nor devirtualise them. R5's
#                          second half: a replay is host code calling host code
#                          and CAN be fused into the loop, where a push callback
#                          reached through a vtable across the .so never can.
#     core-ffi-parse-only  ak_parse_* alone. NOT A DECODE: no object graph is
#                          built. It is the materialisation term on its own.

# THE STRUCTURAL CONTROL. A record is written exactly where the push family
# makes a reverse call, by construction, so `records` must equal `push rev` on
# every shape -- and it does, to the digit, on all thirteen. That is the evidence
# that ONE traversal produced both families (ABI v1 open decision 2's second
# half); a disagreement would mean they had drifted apart on some shape, which
# is what "one traversal emitter, not two" exists to prevent. `pull rev` is 0
# everywhere, which is the family's defining claim, measured rather than assumed.

# AND THE INTERFACE ARGUMENT, which is a property of the descriptor and not of
# this machine (R13): push's reverse column is PER ELEMENT and pull's forward
# column is PER MESSAGE. On P2.2 that is 3,501 reverse calls against 16 forward
# ones. At this host's 1.8 ns it buys nothing; at the java slice's ~80 ns
# reverse call it is 280 us per response.
